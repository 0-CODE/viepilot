## Summary
The second live panel (6 personas + presenter, 3 rounds, 40 messages) was the first with real direct peer
messaging. All 12 round-2 messages were checked in the teammates' transcripts as SendMessage panelist → panelist, so
the engine label "teams" was correct. The run still surfaced 7 defects. One is a wrong rule in the workflow docs
left over from BUG-037. The other six are cases where the panel trusts what an agent says about itself.

## Details

### 1. Wrong pptxgenjs margin order in the workflow (doc regression from BUG-037)
`workflows/proposal.md` (≈ line 1279, "Text in cards") says `margin: [t, r, b, l]`. pptxgenjs actually reads
**[left, right, bottom, top]** (points). Following the doc as written gives off-centre card text. This was
confirmed while building deck v3, where the builder was fixed to `[18,18,6,6]`.

### 2. Presenter `noAnswer` contradicts its cites; no partial state
In round 1 the presenter set `noAnswer: true` on all 11 answers, including answers that drew on the material and
cited it (N3, S4, B11, …). So `unansweredQuestions` reported 11/11. After one correction the result was 3
unanswered and 8 partial. `validateMessage` does not flag `noAnswer: true` together with non-empty `cites`, and the
schema has no `partial` state.
- Expected: either flag the contradiction, or accept `partial: true` (answered from the material, with a named gap).
  The report and the deck gaps should then list a partial answer's missing part separately from a question that got
  no answer at all.

### 3. Panelists miscount their own words; the lead only flags
Five messages went over the 80-word limit (persona 23 in round 2 ×2, 11 in round 2 ×2, 20 in round 3). The agents
reported 63–79 words each time. They count Vietnamese differently from `validateMessage`, which splits on
whitespace so every syllable counts. The prompts say "at most 80 words" but never say how words are counted, and the
workflow only flags messages that go over.
- Expected: the prompts state the rule ("words = space-separated tokens; Vietnamese syllables count one each").
  The workflow has the lead send an over-limit message back for one rewrite before merging. Only a second failure is
  flagged.

### 4. Presenter answers have no message id
Questions get ids (`q7-1`), but the presenter's answers only get a `seq`. Panelists who wanted to answer the
presenter's answer in round 2 could only point `replyTo` at the question id. Two panelists reported this on their
own.
- Expected: `buildTranscript` (or the merge step) gives every message an id, for example `a7-1` for the answer to
  `q7-1`, and the round prompts show those ids.

### 5. Presenter repeats a stock phrase
"mình ghi lại" ("I've noted it") appears in about 10 of the 11 answers. Persona 20 called this formulaic: it reads
as a script, not as honesty. `presenter-prompt.md` has no rule against repetition, and the panel does not run the
existing cliché/repetition checks (curation / humanity) on presenter answers.
- Expected: a prompt rule (say a gap once, in varied words; never end every answer with the same phrase) and a check
  for a phrase repeated in more than ⅓ of the answers.

### 6. No check that a panelist read its round prompt
Persona 23 wrote its round-3 final position without opening `panel-r3-23.md`, working from memory of round 2. The
answer happened to be consistent, but nothing detects this. It is the same class of problem as BUG-036, where
listeners did not open slides.
- Expected: the round prompt carries a per-round token (a nonce, or the id of the latest message) that the
  panelist must echo. The merge rejects or flags a message without it. The workflow tells the lead to check it.

### 7. Provenance and run writing are append-only
- `refreshProvenance` (`lib/proposal-store.cjs`) only adds files it has not seen. It never removes entries for
  deleted files: after a duplicate `simulation/run-2` was removed, its 3 entries stayed in `provenance.json`.
  It also never re-hashes a changed file, because `rel in prov.artifacts` skips it.
- `writeRun` (`lib/proposal-sim-report.cjs`) always makes a new `run-N`. Calling the write step twice by accident
  (seconds apart, identical data) left two identical runs.
- Expected: `refreshProvenance` drops missing entries and updates changed hashes under `simulation/` (sealed
  deliverables stay immutable: report them, never rewrite them). `writeRun` refuses, or asks, when the latest run
  has identical data (same agg hash) unless `force` is passed.

## Acceptance Criteria
- [ ] `workflows/proposal.md` states the pptxgenjs margin order `[left, right, bottom, top]`; a test pins it
- [ ] `validateMessage` flags `noAnswer: true` with cites; `partial: true` is supported in validation,
      `unansweredQuestions` (or a new `partialAnswers`) and the report's panel section
- [ ] panel and presenter prompts state the word-counting rule; the workflow does one rewrite round for
      over-limit messages before flagging
- [ ] every merged message has a unique id (answers included); round prompts show ids; `replyTo` resolves answer ids
- [ ] presenter prompt has an anti-repetition rule; a repeated phrase in more than ⅓ of answers is flagged in the panel
      report
- [ ] round prompts carry a read token; messages without it are flagged; the workflow documents the check
- [ ] `refreshProvenance` removes entries for deleted files and re-hashes changed simulation files (sealed
      deliverables are reported, not rewritten)
- [ ] `writeRun` will not write a duplicate of the latest run without `force`
- [ ] unit tests for all of the above; full suite green

## Discussion
The v3 results should be shown with these caveats. Panel: 4 of 6 would act, all with conditions; personas 7 and 11
would not yet. Personas 20 and 23 changed position. Shared conditions:
- system-recorded logs of the 7/11 runs before day 1 (9, 11, 20)
- written security/legal approval (11, 23)
- one contact per team (7, 23)
- a control group using only plan mode (4, 9)

The hall's key-message recall dropped from 44% to 25% between v2 and v3. The new content may dilute the key
message, so recall should be watched in v4.
