## Summary
Once the proposal type/variant is known, the AI must first build the deck's skeleton (outline), then
decide which repo data fits that skeleton and which does not, and only then start writing slides.
A proposal tells an audience why something matters and what to do next; it is not a record of how
the work was done. Today the flow goes straight from context loading to slide generation, so process
material (CHANGELOG, TRACKER, ROADMAP, phase summaries, commits, request ids) leaks into decks as
"what we did" lists.

## Root cause (current behaviour)
- workflows/proposal.md Step 2 loads the brainstorm session (or a brief) and Step 4 generates the
  manifest directly; no outline step and no curation step in between.
- No rule separates product value from process history; nothing detects version numbers, phase/task
  ids, commit hashes or changelog verbs in slides.
- The persona council (ENH-117c) has no blocker for "process log instead of proposal".

## Design — three gates before any slide content

### Gate 1 — Outline first (Skeleton Gate, MANDATORY)
After type/variant (+ audienceProfile from ENH-119/120) are confirmed, build an outline with no
slide prose yet:
- **Key message**: one sentence the audience must remember.
- **Per slide**: title, arc beat, the slide's **job** (what the audience should think/feel/do after
  it), and the **evidence needed** (number, demo/screenshot, quote, diagram, comparison, none).
- **Per-slide time budget** from the chosen duration.
Shown to the user via AskUserQuestion: approve / edit / reorder / add-remove slides. Slide generation
is blocked until the outline is approved (`--yes` auto-approves and logs it). Stored as
`outline.json` + rendered in the .md summary.

### Gate 2 — Source inventory (deterministic)
Scan candidate sources and classify each one (code, not LLM guesswork):
| Kind | Examples | Default use |
|---|---|---|
| `product-value` | brainstorm session, README value sections, PROJECT-CONTEXT, user brief | primary source |
| `evidence` | metrics, benchmarks, test/coverage numbers, user feedback, case studies | proof slides |
| `architecture` | ARCHITECTURE, system docs, diagrams | only when the audience/variant needs it |
| `visual` | ui-direction, screenshots, prototypes | demo slides |
| `roadmap-future` | ROADMAP *upcoming* items | "what is next" slides, reworded as outcomes |
| `process-log` | CHANGELOG, TRACKER, phase SPEC/SUMMARY/task files, requests, git log, commit messages | never copied; may only be **transformed** into an outcome or a proof point |
| `sensitive` | credentials, .env, internal notes, unreleased/confidential items, personal data | never used |
Users can add sources (`--source <path>`) or exclude (`--exclude <glob>`).

### Gate 3 — Content fit decision (Curation Gate)
For every candidate fact, decide against the approved outline and the audience:
- **FIT** — serves a slide's job for this audience → assigned to that slide.
- **TRANSFORM** — true and useful but phrased as process → rewrite as outcome/benefit/proof
  (e.g. "Phase 165 added 4 voice levels (v3.13.0)" → "You choose how boldly the deck speaks — from
  humble to founder story").
- **DROP** — irrelevant to this audience, too detailed, duplicate, or history with no bearing on the decision.
- **SENSITIVE** — excluded, never shown in slides or notes.
Output a **Content Map**: slide → selected facts (with source + FIT/TRANSFORM + transformed wording);
a **Dropped** list with reasons; open gaps where a slide has no evidence (ask the user rather than
invent — consistent with the Story Brief rule). Shown to the user (AUQ: approve / move items / restore dropped).
Every manifest slide must reference its content-map items; facts outside the map are flagged.

### Anti-changelog guard (validator + council blocker)
- `detectProcessLeak(manifest, {type, variant, audienceProfile})` flags in slides and notes:
  version strings (v3.16.0), phase/task/request ids (Phase 165, ENH-117, BUG-032, T-12), commit
  hashes, file paths and function names (for non-technical audiences), bullets starting with
  changelog verbs (added/fixed/refactored/bumped/merged — vi + en), dated chronological lists,
  "first we… then we…" sequences beyond a threshold.
- Variant-aware allowances: `progress-report`, `leadership-report`, research `progress-report` may
  show milestones **as results vs plan**, never as commit/changelog lists; `tech-architecture` may
  name components.
- Fail-loud: leaks must be fixed (auto-rewrite via TRANSFORM, then re-check) before rendering.
- Persona council blocker added: "process log instead of proposal".

### Prompt contract additions
- "A proposal answers: why this matters to *you*, what changes, why believe us, what we ask. It does
  not narrate how the work was done."
- Slide content may only come from the Content Map.
