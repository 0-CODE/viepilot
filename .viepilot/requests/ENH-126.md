# ENH-126: vp-proposal versioning and upgrade path — what happens to earlier proposals after a ViePilot update

## Summary
When the user updates ViePilot and runs `/vp-proposal` again, earlier proposals must be detected and
handled deliberately: never silently overwritten, upgradable to the new pipeline without redoing
confirmed decisions, and comparable version to version.

## Current behaviour (audit 2026-11-07)
- Output is flat: `docs/proposals/{slug}-{date}.pptx|.docx|.md|-script*.md|-review.md` (`buildOutputPaths`).
- Same-day re-run **overwrites silently** — including any edits the user made in PowerPoint/Word.
- Different-day re-run creates a parallel set with no link to the previous one.
- Nothing records which ViePilot/skill/workflow version produced a proposal or which gates it passed,
  so it is impossible to tell what an old deck is missing (animation 3.15, persona council 3.16,
  purpose consult / variants 3.17, outline + curation ENH-122, backstage ENH-123…).
- The slide manifest and the decisions are not persisted (only the rendered .md), so an old proposal
  cannot be upgraded — only regenerated from scratch.

## Design

### 1. One folder per proposal, immutable versions
```
docs/proposals/{slug}/
  proposal.json                 # identity: slug, title, created, type, variant, lang, currentVersion
  session.json                  # live state (ENH-124), schemaVersion
  versions/
    v1-2026-11-07/              # never overwritten
      {slug}.pptx .docx .md  script*.md  review.md  backstage.md  simulation/ …
      manifest.json             # full slide manifest + outline + content map + decisions
      provenance.json           # viepilotVersion, skillVersion, workflowVersion, generatedAt,
                                # gatesPassed[], inputsHash, artifact hashes
    v2-2026-11-20/ …
```
- Every run creates a new version folder; `proposal.json.currentVersion` points to the latest accepted one.

### 2. Detect existing proposals at start (input gate, AskUserQuestion)
At Step 1, scan `docs/proposals/` for proposals that match the topic/slug (and legacy flat files).
If one exists, ask:
1. **Upgrade** (recommended after a ViePilot update) — keep confirmed decisions and content, run only
   the gates that are new or changed since the version in `provenance.json`, ask only new inputs.
2. **Revise** — new version based on the previous one with the user's changes (routes through ENH-124 Iterate).
3. **New proposal** — separate slug; the old one is untouched.
4. **Keep as is** — open/summarize the existing version, generate nothing.

### 3. Upgrade mode (gate registry)
- A gate registry in code lists each step/gate with the version it appeared or changed in
  (e.g. `animation: 3.15.0`, `persona_council: 3.16.0`, `purpose_consult: 3.17.0`, `outline: ENH-122 version` …).
- Upgrade compares `provenance.viepilotVersion` with the installed version → the list of missing or
  changed gates; reuses `manifest.json` decisions; runs only those gates (with their AUQ gates);
  produces **upgrade-report.md**: what changed, why, new scores vs old.
- Decisions that a new gate needs but the old version never asked (e.g. voice level, audience
  profile, variant) are asked once via AUQ, pre-filled with an inferred recommendation.

### 4. User edits are protected
- `provenance.json` stores artifact hashes. If the .pptx/.docx on disk differs from the stored hash,
  the user edited it → warn before upgrade/revise and offer: import the edited text and speaker notes
  back into the manifest (best effort, shown as a diff for confirmation), keep the edited file as-is
  next to the new version, or proceed and regenerate (the edited file stays in the old version folder).

### 5. Legacy migration
- `vp-tools proposal migrate [--dry-run]` moves pre-existing flat files `docs/proposals/{slug}-{date}*`
  into `docs/proposals/{slug}/versions/v1-{date}/` with `provenance: { viepilotVersion: "legacy" }`;
  never deletes; asks for confirmation (AUQ) and prints the plan first.
- If no `manifest.json` exists (legacy), upgrade first reconstructs a manifest from the .md summary
  (+ .pptx text/notes when available) and asks the user to confirm it.

### 6. Compare and prune
- `vp-tools proposal diff <slug> [vA vB]` — slides added/removed/changed, script length, council
  scores, simulation deltas (ENH-121) between versions.
- `vp-tools proposal prune <slug> --keep N` — confirmation required; current version never pruned.
- `session.json` carries `schemaVersion`; a migration function upgrades older session files on load.

## Acceptance Criteria
- [ ] Folder-per-proposal layout with immutable `versions/v{n}-{date}/`; no run ever overwrites an existing file
- [ ] `manifest.json` + `provenance.json` (versions, gatesPassed, hashes) written for every version
- [ ] Start-of-run detection of existing proposals (incl. legacy flat files) with AUQ: Upgrade / Revise / New / Keep
- [ ] Gate registry with since-versions; Upgrade runs only missing/changed gates, reuses decisions, asks only new inputs; `upgrade-report.md`
- [ ] Hand-edit detection by hash with the three options; edited files never lost
- [ ] `vp-tools proposal migrate` (dry-run, confirm, non-destructive), `diff`, `prune --keep N`
- [ ] `session.json` schemaVersion + migration
- [ ] Workflow + SKILL documented (English only); unit tests with temp project dirs; full suite green
