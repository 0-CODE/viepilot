# BUG-039: Skill `@`-include of the workflow is never loaded; PHASE-STATE template breaks the ENH-118 gate; subagent writes and executor turn budget

- **Created**: 2026-11-17
- **Reporter**: User (found in project smart-ptt / Uaalo with ViePilot 3.24.0, Claude Code)

- **Component**: skill packaging / installer (`skills/vp-*/SKILL.md` ↔ `workflows/*.md`), templates, agents. Adapter: claude-code

## Summary
On Claude Code every `vp-*` skill hands off to its workflow through
`<execution_context>@$HOME/.claude/viepilot/workflows/<name>.md</execution_context>` and
"Execute workflow from `@$HOME/...`". When the skill is invoked with the Skill tool, only the SKILL.md text is
injected. `@` includes are not expanded inside skill bodies, and `$HOME` is not substituted, so the workflow text
never reaches the model. Yet the skills point at hard gates that exist only in the workflow:
- ENH-118 Todo Mirror (vp-auto, vp-evolve)
- ENH-096 orchestrator delegation and the verbatim `{DISPATCH_RULES}` block (autonomous.md)
- BUG-001 doc-first and BUG-003 git persistence details
- brainstorm/crystallize session format and step contracts

Whether the gates apply therefore depends on whether the model chooses to open the file. When it does, it usually
slices these large files with Bash `sed -n`/`grep` (autonomous.md 1206 lines, crystallize.md 2705, brainstorm.md
2485), which the skill's own `<tool_policy>` forbids.

**Verified in this repo (2026-11-17):**
- 15 source skills and 15 installed skills (`~/.claude/skills/vp-*`) contain the literal `@$HOME`.
- `vp-proposal` uses a bare relative `workflows/proposal.md` instead, which is equally not loaded.
- The installer (`lib/`, `bin/`) never rewrites `execution_context`.

## Details

### Steps to reproduce
1. `vp-tools install --target claude-code`.
2. In any project run `/vp-auto` (or `/vp-evolve`, `/vp-crystallize`).
3. Inspect the injected skill content: it shows the literal line `@$HOME/.claude/viepilot/workflows/autonomous.md` and
   no workflow text.
4. The agent either skips ENH-118 / ENH-096, or reads the workflow on its own initiative, often through Bash.

### Expected
The workflow contract is in context when the skill loads, or the skill contains one explicit, deterministic
instruction naming the exact resolved path and the tool to load it with.

### Proposed fix (A preferred)
- **A. Ship the workflow inside the skill at install time.** `vp-tools install --target claude-code` writes the
  workflow as a sibling reference file in the skill directory (for example `references/autonomous.md`), which
  Claude Code skills support. It replaces the `<execution_context>` block with "Step 0 (MANDATORY): Read
  `references/<name>.md` with the Read tool before step 1 (offset/limit for long files); never with Bash". Short
  workflows may be inlined instead.
- **B. Explicit load step with a resolved path.** Same Step 0 as A, but pointing at the absolute
  `~/.claude/viepilot/workflows/<name>.md` path, resolved at install time.
- **C. Hard gates in SKILL.md.** Move every MUST/hard-gate rule (ENH-118, ENH-096 + DISPATCH_RULES, BUG-001,
  BUG-003) into SKILL.md itself, and keep the workflow as optional reference. This can be combined with A.
- Other adapters (Cursor, Codex, Copilot, Antigravity) need the same check: does their skill or agent format expand
  includes?

### R1. PHASE-STATE template does not match the `todo-mirror` parser: the ENH-118 gate always fails (verified)
- `templates/phase/PHASE-STATE.md` uses the heading `## Task Status` (line 9) and columns
  `| # | Task | Status | Started | Completed | Git Tag |`.
- `lib/todo-mirror.cjs` `parseTaskTable()` (line 45) accepts only `^##\s+Tasks\s*$`, with the task id in a `Task`
  column.
- Result: on any project generated from the template, `vp-tools todo check --phase N` reports
  `task-file-without-row` for every task and exits 1, so the mandatory phase-start gate can never pass.
- Fix: change the template to `## Tasks` / `| Task | Title | Status | Started | Completed | Git Tag |`, and also make
  the parser accept the legacy heading and columns so existing projects keep working. Add a test that runs
  `todo check` against a phase dir generated from the template.

### R2. crystallize Step 1B/1C asks research subagents to write the stack cache, which Claude Code blocks (reported)
- Spawned research agents get "Subagents should return findings as text, not write report files" from Write. Every
  write to `~/.viepilot/stacks/{stack}/*.md` fails, and the orchestrator has to rewrite them from the returned text.
  See `workflows/crystallize.md` Step 1B (`research_stack_official`) and Step 1C (`write_stack_cache`).
- Fix: subagents **return** SUMMARY / BEST-PRACTICES / ANTI-PATTERNS / SOURCES as text sections, and the orchestrator
  persists them (ideally `vp-tools stack-cache write --stack <id>` from stdin/JSON, so the format is fixed).

### R3. `vp-task-executor` runs out of turns on scaffold-size tasks (reported; turn cap verified)
- `agents/claude-code/vp-task-executor.md` has `maxTurns: 30`.
- A monorepo scaffold task (Rust workspace + SvelteKit + Android Gradle + iOS XcodeGen + CI) hit the cap twice with
  no report and nothing committed in between.
- Fix:
  - a larger turn budget for M/L tasks, or evolve/crystallize splitting such tasks into one sub-task per platform
  - an executor prompt rule: commit + push after each verified sub-part, and always send a report (PASS / PARTIAL
    with what's left) before the budget runs out
  - the orchestrator treats a missing report as PARTIAL and resumes, never as PASS
